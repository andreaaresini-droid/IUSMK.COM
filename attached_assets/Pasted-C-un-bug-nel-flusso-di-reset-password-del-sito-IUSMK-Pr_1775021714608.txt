C’è un bug nel flusso di reset password del sito IUSMK.

Problema:
l’email di reset arriva correttamente, ma quando l’utente apre il link e prova a salvare la nuova password, compare il messaggio:
“Il link non è valido o è già stato utilizzato”
anche se è il primo utilizzo reale del link.

Questo succede molto probabilmente perché il token viene invalidato troppo presto, ad esempio:
- durante il caricamento della pagina reset-password
- durante una chiamata GET di verifica token
- durante una preview automatica del link da Gmail / iPhone / browser
- prima del vero submit della nuova password

Correggi SOLO questa parte, senza toccare Stripe, corsi, coupon, notifiche, admin o altre funzioni.

OBIETTIVO
Il token reset password deve essere considerato valido fino al vero invio del form “Salva nuova password”.
Deve essere invalidato SOLO dopo reset password completato con successo.

MODIFICHE RICHIESTE

1. NON marcare il token come usato durante:
- GET /reset-password
- validazione iniziale frontend
- apertura pagina
- preview link
- check preliminare del token

2. Marca il token come usato SOLO quando:
- il token è valido
- non è scaduto
- la nuova password è valida
- la password viene aggiornata correttamente nel database

3. Se oggi esiste una logica che invalida il token al primo accesso, rimuovila.

4. Mantieni una validazione separata:
- endpoint GET o check token: solo verifica validità, NON consuma il token
- endpoint POST reset password: aggiorna password e SOLO ALLA FINE consuma il token

5. Aggiungi log backend chiari:
- [RESET_PASSWORD] token ricevuto
- [RESET_PASSWORD] token trovato
- [RESET_PASSWORD] token valido
- [RESET_PASSWORD] token già usato
- [RESET_PASSWORD] token scaduto
- [RESET_PASSWORD] password aggiornata con successo
- [RESET_PASSWORD] token marcato come usato dopo update riuscito

6. Se il token viene aperto da preview/client email, il backend non deve consumarlo.

7. Se esiste un campo tipo usedAt / isUsed:
- aggiornarlo solo dopo successo reale del reset

8. Il frontend deve:
- poter aprire la pagina col token
- mostrare il form normalmente
- inviare la nuova password
- solo allora il backend decide se consumare il token

9. NON modificare la UI se non serve, ma mantieni il messaggio errore corretto se il token è veramente scaduto o già usato.

10. Verifica anche che il token nell’URL venga letto correttamente e passato integro al backend.

RISULTATO FINALE
Flusso corretto:
- utente clicca link email
- si apre pagina reset password
- il token NON viene consumato
- utente inserisce nuova password
- clicca “Salva nuova password”
- backend aggiorna password
- backend invalida token solo dopo successo
- utente vede conferma finale
